Guess, Verify, Undo: KV Caches and Speculative Decoding on an H100

Akshith Macharla

AI chatbots write their answers one token at a time (a token is a word or part of a word). Even on an NVIDIA H100, one of the fastest AI chips, this is slower than we'd expect. The reason surprises most people: the chip isn't short on math power. It spends most of its time waiting for the model to be read from memory. This post shows why, with real numbers, and then explains the trick that speeds it up: a small model guesses the next few tokens, and the big model checks all the guesses in one go.

We build up three ideas in order:

  1. Decoding is memory-bound. Generating each token means reading the whole model from GPU memory.
  2. The KV cache avoids recomputing the past, but it is more data to store and read.
  3. Speculative decoding uses the idle compute to check several guessed tokens at once. Rejected guesses must then be removed from the KV cache, and that is where the real work is.

At the end we look briefly at how production systems like vLLM, SGLang, Modular MAX and Amazon SageMaker handle this. Later posts go deeper into each part.

A few terms first

These are the only terms you need for the rest of the post.

The model we'll use

The examples use Llama 3.1 8B, an open model from Meta. Its text goes in as tokens, and each token becomes a list of 4,096 numbers. Those numbers pass through 32 identical layers, and an output head turns the result into a score for every possible next token.

Every layer has its own weights, so writing even one token means reading all 32 layers: about 16 GB. That cost is what the next section measures. The KV cache box is explained in the section after it.

Decoding one token on an H100

If only one person is using the GPU, Llama 3.1 8B can write at most about 209 tokens per second on an H100. The limit isn't how fast the chip does math. It's how fast the chip can read the model from memory.

The hardware. The H100 has 80 GB of fast memory (called HBM3) that it can read at 3.35 TB/s, that is, 3.35 trillion bytes per second. For math, NVIDIA advertises 1,979 TFLOPS, but that number only applies to specially “sparse” models where half the weights are zero. Normal models like Llama get half of that: about 989 TFLOPS, nearly a quadrillion operations per second.

The model. Llama 3.1 8B has 32 layers and 8.03 billion parameters, and works with 4,096 numbers per token. In BF16 each parameter is 2 bytes, so the weights are 16.06 GB.

One decode step. To produce the next token, the GPU has to multiply the newest token's vector by every weight matrix in all 32 layers. Every one of those 16.06 GB has to travel from HBM to the compute cores.

Work per token Time on H100
Reading the weights 16.06 GB 16.06 GB ÷ 3.35 TB/s = 4.79 ms
Doing the math about 2 FLOPs per parameter = 16.06 GFLOP 16.06 GFLOP ÷ 989 TFLOPS = 0.016 ms

The math takes 16 microseconds; reading the weights takes 4.79 milliseconds, about 300 times longer. So the best possible speed is 1 ÷ 4.79 ms ≈ 209 tokens/s, and the compute cores sit idle more than 99% of the time.

209 is the best case, not what we can actually get. In practice the GPU never reads memory at full speed, and every step has some extra overhead. SGLang's docs show this exact model on an H100, serving one user at a time, running at 158 tokens/s, about three quarters of the limit. Then they turn on speculative decoding (EAGLE-3) and get 373 tokens/s. That's way above 209. How? The limit is for one token per pass, and speculative decoding gets several tokens out of each pass. That's what the rest of this post is about.

Another way to see it: the H100 can do about 989 ÷ 3.35 ≈ 295 FLOPs for every byte it reads before memory stops being the bottleneck. Decoding one token does about 1 FLOP per byte (16.06 GFLOP over 16.06 GB). It is deep in memory-bound territory.

This gap is the opportunity that speculative decoding uses later: if we can give the GPU several tokens to process for the same weight read, the extra math is almost free.

Why the KV cache exists

The KV cache trades recomputation for memory: Llama 3.1 8B stores 128 KiB per token so that it never has to reprocess the past.

What attention needs. In every layer, the new token looks back at all earlier tokens. Each earlier token contributes a key (used to decide how relevant it is) and a value (the information passed along). Both are vectors computed from that token by the layer's weights.

Without a cache. Those keys and values would be recomputed from scratch at every step. At a 4,096-token context, producing one new token would mean running the full model over all 4,096 tokens: about 66 TFLOP, or 66 ms even at the H100's full 989 TFLOPS. That is 14 times slower than the 4.79 ms weight read, and it gets worse with every token.

Where those numbers come from:

  1. Running one token through the model costs about 2 FLOPs per parameter (one multiply and one add per weight): 2 × 8.03 billion ≈ 16 GFLOP per token.
  2. Without a cache, all 4,096 earlier tokens go through the model again: 4,096 × 16 GFLOP ≈ 66 TFLOP.
  3. At the H100's 989 TFLOP per second, that takes 66 ÷ 989 ≈ 66 ms. Here math really is the limit: each weight read from memory gets used 4,096 times.
  4. With a cache, only the new token runs, and the step costs the 16 GB weight read: 4.79 ms. 66 ÷ 4.79 ≈ 14× slower without the cache.

The cost also grows with the text:

Context length Without cache, per new token With cache, per new token
4,096 tokens ~66 ms ~5 ms
8,192 tokens ~132 ms ~5 ms
32,768 tokens ~530 ms ~6 ms

This even leaves out the attention math itself, which grows faster still, so the real cost without a cache is a bit higher.

With a cache. The keys and values of each token are computed once and stored in GPU memory. A decode step then computes K and V only for the newest token, appends them, and reads the stored ones for attention. The prompt is processed once at the start (the prefill) to fill the cache.

How big it is. For each token, Llama 3.1 8B stores a key and a value in every layer. Here's where the size comes from:

Factor Value Why
K and V 2 each token stores a key and a value
Layers 32 every layer keeps its own cache
KV heads 8 not 32: every 4 query heads share one KV head
Numbers per head 128 4,096 ÷ 32 heads
Bytes per number 2 BF16

2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KiB per token (1 KiB = 1,024 bytes).

The model has 32 attention heads but only 8 KV heads. Several query heads share one key/value head (grouped-query attention), which makes the cache 4 times smaller than it would otherwise be.

Only the 8 KV heads are stored, which is where the 128 KiB per token comes from.

The cache also has to be read at every step, on top of the weights (GB here means 10⁹ bytes; KiB means 1,024 bytes):

Context length KV cache size Decode step (weights + cache read)
1,000 tokens 0.13 GB 4.83 ms
8,192 tokens 1.07 GB 5.11 ms
32,768 tokens 4.29 GB 6.08 ms
131,072 tokens 17.2 GB 9.92 ms

At the model's full 128K context, one user's cache is larger than the model itself, and the step takes twice as long.

With many users. Serving many users at once (batching) shares one weight read across all of them, but every user has their own cache. After the 16 GB of weights, the H100 has about 64 GB left: room for roughly 59 users at 8K tokens each, or about 488,000 tokens in total. That is an upper bound: activations, the CUDA context and the serving framework's own reserve take memory too (vLLM uses 90% of GPU memory by default). Even so, at scale the KV cache, not the weights, decides how many users fit on a GPU. That is why production systems put so much effort into its design.

Speculative decoding: four guesses, one forward pass

Normal generation is autoregressive: the model writes one token per decode step, and every decode step is a full forward pass that reads all the weights. So four tokens means four forward passes, one after another, because each token depends on the one before it. Speculative decoding changes that: a small model guesses four tokens, and the big model checks all four in a single forward pass. Four tokens, one weight read.

The two models. For this part we switch from Llama to Qwen3, because Qwen3 comes with a small sibling model that uses the same tokenizer, and the draft needs that. The target is the model whose output we want: Qwen3-8B, 36 layers, 16.4 GB in BF16. The draft is the small model that guesses ahead: Qwen3-0.6B, 28 layers, 1.2 GB. Each draft step reads about 14 times less data than a target step.

Without speculation, four tokens take four target passes: 4 × 4.89 ms ≈ 19.6 ms.

With speculation, the draft guesses four tokens at a time. Four is just an example: the number of guesses is a setting, and engines often use somewhere between 2 and 5.

Say the text so far is “The cat” and the right continuation is “ sat on the mat”. Tokens are written with their leading space, the way tokenizers store them: “ sat” is one token. Below, a dot marks that space: ·sat.

  1. Draft four tokens. The 0.6B model runs four steps, one after another, and guesses ·sat, ·on, ·a, ·mat.
  2. Verify in one pass. The target runs once on five positions together: the last accepted token ·cat plus the four guesses. A causal mask lets each position see the target's KV cache plus only the positions before it, so in this single pass:
    • the ·cat position predicts what follows “The cat”, which checks guess 1 (·sat);
    • the ·sat position sees “The cat sat”, which checks guess 2 (·on);
    • the ·on position checks guess 3 (·a), and so on up to the last position, which predicts a bonus token after all four guesses.
  3. Accept or reject, left to right. The target agrees with ·sat and ·on. At guess 3 it wanted ·the, not ·a. So ·a is rejected, ·mat after it is thrown away too (it was built on a wrong token), and the target's own ·the is used instead.
Target input:      cat     sat     on      a       mat
Target predicts:   sat     on      the     (ignored after the first miss)
Draft guessed:     sat     on      a       mat
Result:            keep    keep    miss: use "the", drop "a" and "mat"

Result: three tokens (“sat on the”) from one target pass. Verifying five positions instead of one costs almost nothing extra: the weights are read once either way, and the extra math is microseconds.

Each model keeps its own KV cache, so after the miss both caches hold entries for words that are no longer in the text. Cleaning those up is the next section.

What one round costs. A round means: the draft model guesses 4 tokens, and the target checks all 4 in one pass.

In the cat example, the target accepted 2 of the 4 guesses (“ sat” and “ on”) and added 1 token of its own (“ the”, in place of the wrong guess “ a”). So one round gave us 2 + 1 = 3 tokens.

Every round ends the same way: you keep the guesses the target agreed with, plus 1 token the target writes itself. If a guess is wrong, the target's token replaces it. If all four guesses are right, the target still adds one more token after them for free, because its check pass already predicted what comes next.

What happens Guesses kept Target's own token Tokens this round
The first guess is wrong 0 1 1
Our example: the third guess is wrong 2 1 3
All four guesses are right 4 1 5

So even in the worst case, a round still gives 1 token (the target's own), the same as normal decoding.

Now compare three ways of getting those same 3 tokens:

  1. No draft model at all. The target writes all 3 tokens itself, one forward pass per token. Each pass takes 4.9 ms, the time to read Qwen3-8B's 16.4 GB of weights at 3.35 TB/s.
  2. A draft model running at its top speed. Each guess takes 0.36 ms, the time to read the draft's 1.2 GB of weights. A real draft never runs this fast; this is the best it could ever do.
  3. A draft model that takes 3 ms per guess. A model this small wastes time on every step starting a few hundred tiny GPU jobs, and that can cost more than the actual work. 3 ms is an example of what that looks like.
1. No draft model 2. Draft at top speed 3. Draft at 3 ms per guess
Guessing 4 tokens none 4 × 0.36 = 1.4 ms 4 × 3 = 12 ms
Target passes 3 × 4.9 = 14.7 ms 1 × 4.9 = 4.9 ms 1 × 4.9 = 4.9 ms
Total for 3 tokens 14.7 ms 6.3 ms 16.9 ms
Per token 4.9 ms 2.1 ms 5.6 ms

With a draft at top speed, we get the 3 tokens more than twice as fast. With a draft at 3 ms per guess, it's slower than not using a draft at all. The tipping point is about 2.45 ms per guess. So speculative decoding only pays off when guessing is cheap, and that's what the newer methods later in this post compete on.

Why the answer doesn't change. A guess only survives if the big model agrees with it. With greedy decoding, agreeing means it's the big model's top pick. With sampling, a guess is kept or thrown out based on how likely each model thought it was, and when one is thrown out, the replacement is chosen to make up the difference. The math works out so the text comes out as if the big model had written it alone. The small model only changes how fast you get there. (The exact rule: a guess is kept with probability min(1, p/q), where p and q are how likely the big and the small model rated it; if it's rejected, the replacement is sampled from what's left over, max(0, p − q).)

How much it helps. That depends on how often the guesses are right. If each guess is right 75% of the time:

Guesses per round Tokens per round, on average
1 1.75
2 2.31
4 3.05
8 3.70

More guesses help less and less, because a guess only counts if every guess before it was right too. And a round only pays off if the guessing is cheap, which is what the newer methods later in this post compete on.

When the target rejects: cleaning up two caches

Every rejected guess leaves wrong keys and values behind in both the target's and the draft's KV cache, and they must be removed before the next round.

Take the example above. Before the round, both caches hold only “The”. Here is what each model wrote during the round:

Cache Wrote K/V for Keep Remove
Target (Qwen3-8B, 144 KiB per token) ·cat ·sat ·on ·a ·mat ·cat ·sat ·on ·a ·mat (288 KiB)
Draft (Qwen3-0.6B, 112 KiB per token) ·cat ·sat ·on ·a ·cat ·sat ·on ·a (112 KiB)

The draft never wrote K/V for ·mat: it produced ·mat as the output of its fourth step but never fed it back in. The accepted correction ·the is in neither cache yet; both models process it as the first input of the next round.

The opposite case matters too. If all four guesses are accepted, the target's cache holds all four guesses, but the draft's is two tokens behind: it is missing ·mat (never fed back) and the target's bonus token. The next round must run the draft on both before it can guess again.

If the wrong entries stay, the next round would read an ·a that isn't in the text, and the output would quietly go wrong. So the rule is simple: the next round must never see rejected entries.

There are three common ways to do this:

  1. Move a counter back. Keep a count of how many tokens in the cache are real. After a miss, lower the count by the number of rejected tokens. The wrong entries are still in memory, but nothing reads them, and the next round writes over them. vLLM works this way.
  2. Write guesses somewhere temporary. Put the guesses' K/V in a scratch area, and copy only the accepted ones into the real cache.
  3. Fix the draft's cache too. Remove the draft's rejected entries. If all the guesses were accepted, feed the draft the tokens it missed. SGLang does this after every check.

One more rule: never share a guess before it's checked. vLLM lets different requests reuse each other's cached prompts, and it only shares tokens the target has confirmed.

Some methods make this harder. Methods like EAGLE-2 guess a small tree of options at each position instead of a single line, so the accepted tokens end up scattered in the cache instead of sitting neatly at the end. I'll explain how these methods work, and compare them, in an upcoming post.

Moving a counter back is the cheapest fix, but it only works if the wrong entries sit at the end and writing them didn't overwrite anything we still need. Whether that's true depends on how the KV cache is built, which is the next section.

KV cache designs in production

Every KV cache design trades memory for something, and the designs that throw tokens away are exactly the ones where undoing a rejected guess gets hard.

Some designs keep every past token and only change how it's stored. Others throw tokens away to save memory. That difference decides how hard it is to undo a wrong guess:

Design What it does Undoing a wrong guess
Dense One block of memory per user, every token kept Easy: move the counter back
Paged (vLLM) Memory split into small pages, the way an operating system does it, so less is wasted Easy: move the counter back
Prefix sharing (SGLang) Users with the same prompt share its cache Easy, as long as guesses are never shared before they're checked
Grouped-query attention (Llama 3, Qwen3) Several query heads share one KV head, so the cache is smaller (4× for Llama 3.1 8B) Easy: every token is still kept
Latent compression (DeepSeek) One compressed vector per token instead of full K and V Easy: every token is still kept
Quantized (FP8, KIVI) K and V stored with fewer bits Usually easy; depends on when values get compressed
Sliding window (Mistral) Keeps only the most recent tokens Hard: guesses push out tokens you still need
Sinks + recent (StreamingLLM) Keeps the first few tokens plus the most recent ones Hard: same problem
Importance eviction (H2O) Keeps recent tokens plus the ones that got the most attention Hardest: guesses also change which tokens get thrown out

The last column is my own reasoning, based on how each design stores tokens. The papers that introduced these designs don't cover speculative decoding, so none of them tested this.

The problem in miniature. Take a cache that keeps only the last three tokens, and write the four guesses into it:

Committed:        [A]  [B]  [C]
write d1   ->     [B]  [C]  [d1]
write d2   ->     [C]  [d1] [d2]
write d3   ->     [d1] [d2] [d3]
write d4   ->     [d2] [d3] [d4]

Target accepts d1, rejects d2.
Correct cache:    [B]  [C]  [d1]
What is left:     [d2] [d3] [d4]

No counter can bring back B and C. They were pushed out by guesses that turned out to be wrong.

Every cache that keeps only some tokens, like sliding windows and H2O, runs into this in some form. The usual fix is to write guesses somewhere temporary and commit only the ones the target accepts. I'll go through each of these cache designs, and how they handle rejected guesses, in an upcoming post.

Speculative decoding methods in production

Production engines don't all guess the same way, but the trend is simple: make each guess cheaper.

Method Who does the guessing In short
Draft model A separate small model, like Qwen3-0.6B for Qwen3-8B Easy to set up, but every guess runs a whole model
N-gram No model: it copies what came after the same words earlier in the text Almost free; works best when the output repeats the input
EAGLE One extra layer that reads the big model's own hidden state Cheap and accurate, but trained for one specific model
MTP Extra prediction layers built into the model when it's trained Used by DeepSeek-V3
P-EAGLE, DFlash Small drafters that guess several tokens in one pass No more guessing one token at a time

vLLM and SGLang support most of these. Modular MAX supports EAGLE, MTP and DFlash for specific models, and Amazon SageMaker can train an EAGLE drafter on your own data.

Where it stops helping. Speculative decoding uses spare GPU time. With one user, the GPU spends most of its time waiting on memory, so there's plenty to spare. With many users at once, the GPU is already busy, and every wrong guess is wasted work. That's why MAX lets you set fewer guesses for bigger batches, and SGLang can change the number of guesses while it runs, based on how many are being accepted.

I'll explain how these methods work, and compare them, in an upcoming post.

Takeaways

  • Writing text for one user is limited by memory, not math. Llama 3.1 8B has to read all 16 GB of its weights for every token, so an H100 tops out around 209 tokens per second.
  • The KV cache saves the past so the model doesn't redo work. For Llama 3.1 8B that's 128 KiB per token. With long texts or many users, the cache, not the model, decides how many people fit on one GPU.
  • Speculative decoding lets a small model guess and the big model check. The big model checks several guesses in one pass. The output stays the same; it just arrives faster.
  • It only helps if guessing is cheap. A slow draft can make things slower than not guessing at all.
  • Every wrong guess has to be removed from both caches. That's easy when the cache keeps every token, and hard when it throws tokens away.
  • Newer methods all chase the same goal: EAGLE, MTP, P-EAGLE and DFlash each make guessing cheaper.
