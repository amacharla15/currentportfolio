MAX vs vLLM on an H100, One Year Later

Akshith Macharla · November 2, 2026

What MAX is

MAX is Modular's inference server. max serve exposes an OpenAI-compatible endpoint, the same way vllm serve does. Underneath, it doesn't run PyTorch: each model is written as a graph in MAX's Python API, compiled ahead of time by MAX's own graph compiler, and run on kernels written in Mojo, Modular's programming language.

Startup does the expensive work once; after that, every decode step replays a compiled program. With version 26.7 on October 22, 2026, Modular made MAX's full source available. The serving code, models and kernels are Apache 2.0, and the graph compiler and runtime are under the source-available MAX License.

MAX vs vLLM, layer by layer

The two servers look the same from the outside and are built alike down to the KV cache. They split at the model itself.

Why compile the whole graph ahead of time

MAX trades a slow first start for a model that runs as one compiled program, and for code that can target more than one GPU vendor. Modular's own architecture spec lists its goals in priority order: portability, productivity, performance.

What it buys:

  • Fusion across the whole model. The compiler sees every operation at once, so it can merge neighbors into one kernel. One example from the 26.5 release notes: query/key RMSNorm followed by RoPE now runs as a single kernel.
  • One codebase, several vendors. The compiler picks kernels by their signature, and the kernels specialize internally for each device. Supporting a new GPU is then mostly kernel, driver and runtime work.
  • Almost no Python in the loop. Each step replays a compiled program through CUDA graphs. In my run at batch 1, the client measured 5.46 ms per token against 5.43 ms of logged GPU time.
  • One artifact for every KV-cache setting. Cache size and paging are runtime parameters, so changing them doesn't recompile.

What it costs:

  • Cold start. The spec itself says cold start is "non-trivial (~3 minutes for 405B)". In my run, MAX's log reports 182 s of graph compilation for the 8B model (130 s for the model itself), and the result is cached for later starts. I'm not comparing total startup times: MAX's first start also included minutes of Python imports from a network volume and a 133-second weight download that vLLM later reused, so its total says more about my setup than about MAX. Modular's 26.7 post says MAX now has full eager-mode support, which reached a first token in about 30 s, against about 110 s compiled, on a slice of Gemma 4 31B.
  • Every model is a rewrite. A model has to be written in MAX's graph API before MAX can serve it; there's no running an arbitrary PyTorch model. Modular is also not accepting new models from outside contributors right now.
  • Speed depends on Modular's own tuning. Where a GPU and weight shape haven't been tuned, MAX uses a generic kernel configuration or falls back to cuBLAS. That turns out to matter in my benchmark.

What Modular says about performance

Modular reports MAX beating vLLM on Blackwell GPUs. On the H100 its record is mixed: it shipped Hopper matmul kernels in 2025 and small-batch Hopper tuning for "specific shapes" in early 2026, then said in September 2026 that the H100 isn't its focus.

My benchmark, in short

Serving Llama-3.1-8B-Instruct in bf16 on one H100 SXM, MAX has roughly halved its gap to vLLM in a year. In October 2025, MAX 25.6 produced about 40% fewer tokens per second than vLLM under load; today, MAX 26.7 produces about 20% fewer than vLLM 0.32.

  • With one user, MAX is faster: 10–14% more tokens per second than vLLM, and a lower time to first token on short prompts.
  • With 8 or 32 users, vLLM is faster: MAX produces 14–22% fewer tokens per second, and each token takes longer.
  • The gap opens between batch 1 and batch 2. MAX's own logs show its GPU time per decode step jumping from about 5.5 ms at batch 1 to about 8.3 ms at batch 8. With one request, MAX uses a kernel that keeps the whole GPU reading weights. With two or more, two of Llama-8B's four weight matrices get a generic setting that uses only 16 of the H100's 132 cores. The code shows the switch; I haven't yet measured how much of the slowdown it explains.

Where this started

In October 2025, a user on Modular's forum benchmarked MAX 25.6 against vLLM 0.10.1.1 on an H100 serving Llama-3.1-8B-Instruct. With NVIDIA's GenAI-Perf at 10 concurrent users, 200-token prompts and 200-token outputs, MAX produced 800 output tokens/s against about 1,324 for vLLM. Its average time to first token was 40 ms against about 20 ms.

Both servers ran with default settings. Modular staff reproduced the gap and opened an internal ticket to investigate it.

I wanted to see how much that has changed by MAX 26.7, measured with a harness anyone can rerun.

Setup

Both servers ran on the same RunPod pod, one at a time, with their default scheduling settings. Everything in this table comes from my launch commands or the servers' own startup logs.

Hardware: 1× NVIDIA H100 80GB HBM3 (SXM), driver 595.91.07, CUDA 13.2, 16 vCPUs. The benchmark client ran on the same pod.

Workload: three tests, each at 1, 8 and 32 concurrent users. Each user sends its next request as soon as the last one finishes.

  • short: one short question; about 56 prompt tokens including the chat template.
  • long: about 1,500 words of unique random text, then a question. Prefill-heavy.
  • shared: the same 1,500-word system prompt on every request, measured with that prefix already cached.

Rules:

  • Every request generates exactly 256 tokens (ignore_eos, temperature 0, streaming). 100 requests at 1 and 8 users, 320 at 32 users.
  • Token counts come from each server's usage report, not from counting stream chunks.
  • Time per output token (TPOT) = (last token time − first token time) ÷ (tokens − 1), per request.
  • Each run's prompts start with a run-specific tag, so no run can reuse another run's cache.
  • One run per configuration, with zero errors and zero short outputs in every run.

MAX's average time to first token is now lower than vLLM's on this test, but its tail is worse: p99 of 188 and 233 ms in its two runs, against 142 ms for vLLM. Both servers' absolute TTFTs are higher than in the forum's run, which is one reason to compare ratios rather than raw numbers.

Where the remaining gap comes from

MAX's time per token jumps by half between 1 and 8 users, while vLLM's barely moves. That jump is the throughput gap.

It's GPU work, not server overhead. MAX logs the GPU execution time of each step. Its median was 5.4–5.7 ms at batch 1, 8.3 ms at batch 8, 8.2 ms at batch 10, and 9.3 ms at batch 32. At batch 1, the time per token my client measured (5.46 ms) is within 0.03 ms of the logged GPU time (5.43 ms).

It shouldn't cost that much. Generating one token reads every weight once: 16 GB in bf16. At the H100 SXM's 3.35 TB/s that takes 4.8 ms, so MAX at batch 1 runs at about 89% of peak memory bandwidth. A batch of 8 reads those same weights once for all 8 users, so its step should take almost the same time. MAX's batch-8 step reaches about 58%.

Where the time goes. MAX's H100 matmul code picks a kernel by how many requests are in the batch (dispatch.mojo, commit a431ffa):

  • One request: a kernel built for a single row (a GEMV), used for every model (line 1011). It keeps the whole GPU reading weights, so MAX runs near the hardware limit.
  • Two or more requests: a general matmul that looks up tuned settings for the exact weight shape. The bf16 H100 table covers shapes from models such as Llama 3.3 70B and Gemma 3 27B, but none of Llama-3.1-8B's four, so they get one generic setting (line 1794). There is a tuned H100 table for exactly these four shapes, but only for FP8 weights (line 514).

The generic setting splits each weight matrix into chunks of 256 output columns and gives each chunk to one of the H100's 132 SMs, its cores. With 2 to 64 requests in the batch:

Weight matrixOutput × inputSize per layerChunks = SMs working, of 132
QKV6144 × 409650 MB24
Attention output4096 × 409634 MB16
Gate/up28672 × 4096235 MB112
Down4096 × 14336117 MB16

A decode step is limited by how fast weights are read, and reading is fastest when many SMs read at once. Here the attention-output and down matrices, about a third of each layer's weights, are read by 16 SMs while the other 116 wait. That fits both of Modular's statements: "H100 isn't included yet," and small-batch Hopper tuning for "specific shapes." Llama-3.1-8B's bf16 shapes aren't among them.

What this doesn't prove yet. The code path and tile counts come from MAX's source; their cost doesn't. I haven't profiled a step, and attention also changes with batch size, so I can't yet say the matmuls account for all of the extra 2.7 ms.

What I'd check next

The explanation can be tested in about an hour of GPU time, and if it holds, the fix starts with tooling MAX already has. The mechanism below is checked in MAX's source; the time it would save isn't measured yet.

Confirm the cause:

  1. Sweep batch sizes 1, 2, 4, 8 and 16. A jump already at 2 points to a code-path switch, not growing load.
  2. Profile one decode step at batch 1 and at batch 8 with Nsight Systems. MAX has this built in since 26.4 (CLI docs): launch the server under nsys launch and max benchmark --profile prints a ranked table of GPU kernels. If the extra 2.7 ms sits in the matmul kernels, it's the dispatch; if it's in attention or in idle gaps between kernels, it isn't.
  3. Time the four weight shapes on their own with MAX's kbench, for batches of 1 to 64.

Where a fix would start, if the matmuls are the cause:

  • Swap A and B for these shapes. MAX's own config builder says that when the batch is small compared to the output width, swapping the two inputs "improves SM utilization" (config.mojo). Swapping cuts each matrix along its 4096 output columns, in pieces of 64. MAX already does this for a 4096 × 1536 matrix with fewer than 41 requests (line 1815), where the same 4096 columns become 64 chunks instead of 16.
  • Or add tuned entries for these shapes. MAX's H100 table is generated by Modular's kprofile tool from an autotuning spec, tuning_table_bf16.yaml. Covering these four shapes for 2 to 128 requests means new entries, not a new kernel.

The target: if the batch-8 step stayed near its batch-1 time of about 5.5 ms, MAX would beat vLLM's 6.35 ms at that load.

If the profile confirms it, I'll share it with Modular as a GitHub issue, with the profile and kbench numbers attached. MAX's kernel code currently accepts bug fixes only.

Two other differences worth knowing

Prefix-cache granularity. MAX's KV cache stores tokens in 128-token pages; vLLM's blocks hold 16 tokens. A shared prefix shorter than one page is never reused. In the short test, every prompt in a run shares the chat template and my run tag: vLLM served 60.3% of prompt tokens from cache, MAX 0%. In the shared test, the hit rates were 95.9% (MAX) and 98.9% (vLLM). For real traffic, this matters when many requests share a short system prompt.

Tail latency with long prompts. At 32 users in the long test, vLLM's p99 gap between streamed tokens was 123 ms; MAX's was 23.8 ms. MAX's median time per token was still worse (12.6 ms vs 10.6 ms). vLLM schedules prefill chunks in the same steps as decoding, while MAX runs prefill in separate steps by default. I haven't traced which part of that produces the difference.

Caveats

  • One run per configuration. The two AIPerf runs of MAX agreed within 2%, but I'd treat differences under about 5% as noise until the full matrix is repeated.
  • One GPU, one model, one precision. These results say nothing about FP8, larger models, multiple GPUs, or AMD hardware.
  • Default scheduling only. MAX can mix prefill and decode in one step with --enable-in-flight-batching; I didn't test it.
  • Closed-loop load. Each user waits for its answer before sending the next request. A fixed request-rate (open-loop) test can rank servers differently.
  • Client on the same machine. The load generator shared the pod's 16 vCPUs with the server.
  • The 2025 comparison is a ratio, not a rerun. The forum test used GenAI-Perf, older versions, and an H100 whose variant wasn't stated. Compare the MAX-to-vLLM ratios, not the absolute numbers.

Reproduce it

The harness is three small files, bench.py, run_all.sh and compare.py, on GitHub at amacharla15/KernelPref, along with this run's CSV, both server logs and the AIPerf outputs. Use a fresh virtual environment for each server, on local disk, and upgrade pip first: an old pip can fail to install either package, and on a network volume Python imports alone can add minutes to startup.

# MAX
pip install -U pip
pip install "max[serve]==26.7.0" openai
max serve --model meta-llama/Llama-3.1-8B-Instruct --quantization-encoding bfloat16 \
  --max-batch-size 64 --device-memory-utilization 0.9 > max.log 2>&1 &
until curl -sf localhost:8000/v1/models >/dev/null; do sleep 5; done
./run_all.sh max rep1

# vLLM (after stopping MAX)
pip install -U pip
pip install "vllm==0.32.0" openai
vllm serve meta-llama/Llama-3.1-8B-Instruct --dtype bfloat16 --max-num-seqs 64 \
  --gpu-memory-utilization 0.9 --enable-prompt-tokens-details > vllm.log 2>&1 &
until curl -sf localhost:8000/v1/models >/dev/null; do sleep 5; done
./run_all.sh vllm rep1

python compare.py max vllm
